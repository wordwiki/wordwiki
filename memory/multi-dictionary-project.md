Direction set 2026-07-24: a researcher offered several dictionaries — the gold one a ~30K-entry transcription of RAND into Listuguj (+ some SF). NOT merged into MMO: separate dictionaries, one app server, entries copyable with provenance links. Each dictionary: its OWN assertion table (separate-tables decision is FINAL — dz; wordwiki/multi-dictionary-support.md predates the discussion and is mostly superseded, incl. its dictionary_id sketch), its OWN soft schema loaded as DATA, its own published static site + home content, with cross-dictionary public search (primary first, foreign hits badged + linked over) and cross-site audio via the shared content-addressed stores. End goal: port dz's Java shoebox .typ parser → load an external dictionary and edit it directly (shoebox/toolbox replacement). Import model (dz): .typ import is LITERAL/lenient (raw-rand as-is); cleanup happens IN-SYSTEM via a rand→reshaped-rand dictionary transform (so dictionary creation must be cheap ceremony) — the offline java→python→import-mmo pipeline pattern is retired (import-mmo.ts = completed one-shot, never runs again). Public search (dz 2026-07-24): the CSS-selector home-page search gets REPLACED by an offline JS-index search — the OFFLINE invariant stays (survives server death, works from file://, so index via <script src> not fetch); separable, can land before the multi-dictionary phases. Site-editor requirements brought forward (dz 2026-07-24, survey §2.8): dumps stay THE publish interface — simple json + a few-imports REFERENCE static-site generator is the look-and-feel escape hatch other language projects need (core adoption requirement, not archival nicety); public pages must ALSO render LIVE (preview routes over an in-memory PublishSource) because the site-editor flow is broken without page preview. Site editor itself is still raw ("needs fiddling"). Watson (the researcher, now 90) is MMO's ancestral author — his dictionary of ~25 years ago became shoebox-MMO (java static generator; Sfm.java was its front end) which became wordwiki; his current drop (repo watson/ + watson.txt) is a work-in-flight pipeline (raw Rand queue + Ng/Lk orthography-forked "Final" pairs) that wordwiki's variant lanes reunify. Licensing settled: CC-share-alike like MMO, kept separate, ATTRIBUTION TO WATSON.

Doc of record: **wordwiki/multi-dictionary-survey.md** (2026-07-24 four-agent survey) — what's already generic, the hard-coding inventory, choices, and the 6-phase staged plan (0 grout → 1 schema roles → 2 schema-as-data+registry → 3 multi-store+routes → 4 publish+cross-search → 5 .typ import). Key survey facts: schema literal already 100% JSON-serializable; assertion SQL layer fully table-parameterized; DictionaryStore one ctor-arg from multi-instance (assertionTable='dict' at :35); render-entry-meta is already THE public renderer; real work = typed Entry world (choke point: dictionary-store entries/publishedProjection casts), ~11 semantic roles hardwired to MMO relation names, ~14 raw-dict-SQL files, ~163 routes/~150 URL literals, publish content constants. Regression oracle: publish --from=dump byte-identical tree diff.

**Why:** RAND is a historical source; keeping it a unit preserves provenance/scholarly integrity; MMO stays the voiced/vetted primary. Multi-schema makes the tool reusable for other language-preservation projects.

**How to apply:** read the survey doc before touching this; peers consume PROJECTION artifacts, never each other's schemas; leaf MMO reports may stay typed — core (editor/versioning/publication/feeds/search/publish traversal) must be role/schema-driven.
